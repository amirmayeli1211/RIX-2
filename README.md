# RIX STORM PANEL 2.1 — Flat Edition (Xray API)

نسخه بازطراحی‌شده و تخت برای مدیریت کاربران Xray. تمام فایل‌های پروژه در ریشه ZIP هستند و پوشه اضافی داخل ZIP وجود ندارد.

فایل‌های `preview-dashboard-dark.png` و `preview-dashboard-light.png` تصاویر جداگانه تم تیره و روشن‌اند؛ تصاویر `preview-nodes.png`، `preview-clients.png`، `preview-mobile.png` و `preview-subscription.png` نیز فقط پیش‌نمایش رابط با اطلاعات ساختگی هستند، نه خروجی سرور واقعی.

> **نکته درباره منشأ و دیتابیس:** این بسته بازسازی‌شده بر پایه نیازهایی است که برای مخزن عمومی `amirmayeli1211/RIX-1` توضیح داده شد؛ فایل‌های کامل اصلی نتوانستند مستقیماً به محیط ساخت منتقل شوند، بنابراین این یک patch خط‌به‌خطِ همان repository نیست و دیتابیس آن با نسخه 2.0 تضمین‌شده سازگار نیست. ابتدا در یک Railway service و Volume آزمایشی جداگانه بررسی کن؛ سرویس یا دیتابیس قبلی را با این بسته جایگزین نکن مگر پس از انتقال و آزمایش داده‌ها.

## این نسخه چه کار می‌کند؟

- ساخت کاربر از یک فرم: پروتکل، روش انتقال، امنیت، حجم و مدت اعتبار.
- پشتیبانی از پروتکل‌های **VLESS، VMess، Trojan و Shadowsocks** با محدودیت‌های سازگار هرکدام.
- انتقال‌های TCP، WebSocket، gRPC و XHTTP برای ترکیب‌های پشتیبانی‌شده.
- برای هر کاربر یک inbound و پورت اختصاصی در Xray ایجاد می‌کند؛ خاموش/روشن‌کردن و حذف کاربر نیز از طریق Agent به Xray فرستاده می‌شود.
- صفحه اشتراک خصوصی، نمایش لینک/کانفیگ و QR Code.
- رابط فارسی راست‌چین با تم تیره و روشن.
- رمزگذاری اطلاعات حساس ذخیره‌شده و محافظت CSRF برای فرم‌ها.

**حجم و انقضا:** انقضای زمانی به شکل خودکار بررسی می‌شود. این نسخه هنوز شمارنده زنده مصرف ترافیک Xray را پیاده نکرده است؛ مقدار مصرف فعلاً دستی ثبت می‌شود و نباید به‌عنوان اندازه‌گیری زنده حجم در نظر گرفته شود.

## معماری ساده

دو بخش لازم است:

1. **پنل مدیریتی** روی Railway اجرا می‌شود. صفحه وب، کاربران، اشتراک‌ها و دیتابیس را نگه می‌دارد.
2. **Xray-core و RIX Agent** روی یک VPS واقعی که قرار است ترافیک VPN را عبور دهد اجرا می‌شوند. Agent به شکل احراز هویت‌شده، درخواست ساخت/حذف inbound را به API محلی Xray می‌فرستد.

Railway فقط محل اجرای پنل است؛ آن را به‌جای VPS واقعی VPN فرض نکن. برای ارتباط کلاینت‌ها باید روی VPS پورت‌های انتخاب‌شده باز باشند و دامنه/IP داخل کانفیگ واقعاً به همان سرویس برسد.

## بخش اول — استقرار پنل روی Railway

1. این فایل‌ها را از ZIP استخراج کن یا محتویات را در ریشه مخزن GitHub خودت قرار بده؛ `Dockerfile` در ریشه است.
2. در Railway یک سرویس جدید از repository ایجاد کن. Railway به‌صورت خودکار Dockerfile را تشخیص می‌دهد.
3. در بخش **Variables** متغیرهای زیر را تعریف کن:

| Variable | چه مقداری وارد کنم؟ |
|---|---|
| `APP_ENV` | `production` |
| `APP_NAME` | `RIX STORM PANEL 2.1` |
| `SECRET_KEY` | رشته تصادفی محرمانه حداقل ۴۰ کاراکتری؛ نمونه امن را با `python -c "import secrets; print(secrets.token_urlsafe(48))"` بساز |
| `DATA_ENCRYPTION_KEY` | کلید Fernet؛ با دستور `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` بساز |
| `ADMIN_USERNAME` | نام ورود مدیر، مثلاً `admin` |
| `ADMIN_PASSWORD` | رمز قوی و یکتا با حداقل ۱۶ کاراکتر |
| `PUBLIC_BASE_URL` | دامنه عمومی HTTPS سرویس Railway، بدون `/` پایانی؛ مانند `https://your-panel.up.railway.app` |
| `DATA_DIR` | `/data` |
| `DATABASE_URL` | خالی بگذار تا SQLite داخل `/data/rix_storm.db` استفاده شود |
| `SESSION_MAX_AGE_SECONDS` | `28800` |

4. در Railway برای سرویس، یک **Volume** بساز و به مسیر `/data` وصل کن. بدون Volume، فایل دیتابیس SQLite ممکن است با استقرار مجدد از بین برود.
5. در بخش Networking دامنه عمومی برای پنل بساز، سپس مقدار دقیق آن را در `PUBLIC_BASE_URL` قرار بده و Redeploy کن.
6. پنل را باز کن و با `ADMIN_USERNAME` و `ADMIN_PASSWORD` وارد شو.

`PORT` را دستی وارد نکن؛ دستور راه‌اندازی از متغیر `PORT` خود Railway استفاده می‌کند.

**کلیدها را در فایل GitHub یا چت عمومی قرار نده.** اگر `DATA_ENCRYPTION_KEY` را بعداً عوض کنی، اطلاعات محرمانه‌ای که با کلید قبلی ذخیره شده‌اند دیگر رمزگشایی نمی‌شوند؛ آن را در جای امن نگه دار.

## بخش دوم — آماده‌سازی Xray روی VPS واقعی

این بخش نیاز به دسترسی مدیریتی به VPS دارد. اگر Xray از قبل کاربران یا کانفیگ فعال دارد، قبل از تغییر فایل آن نسخه پشتیبان بگیر و تنظیمات فعلی را بازنویسی نکن.

### 1. روشن‌کردن Xray API به شکل محلی

در کانفیگ فعلی Xray، بخش API زیر را با ساختار موجود **ادغام** کن؛ این بلوک به‌تنهایی یک فایل کامل Xray نیست و فقط برای نسخه‌های جدید Xray-core (از 1.8.12 به بعد) از حالت ساده API استفاده می‌کند:

```json
"api": {
  "tag": "api",
  "listen": "127.0.0.1:10085",
  "services": ["HandlerService", "LoggerService", "StatsService"]
}
```

اگر از قبل بخش `api` داری، بخش‌ها را با هم ادغام کن و پورت/آدرس را با `XRAY_API_ADDR` هماهنگ کن. API فقط روی `127.0.0.1` بماند و پورت `10085` را در فایروال عمومی باز نکن. در نسخه‌های قدیمی‌تر، طبق راهنمای رسمی باید inbound و routing مخصوص API را جداگانه تنظیم کرد.

### 2. نصب Xray رسمی و Agent

فایل‌های `install_xray_agent.sh` و `xray_agent.py` را روی VPS در یک پوشه قرار بده، سپس در همان پوشه اجرا کن:

```bash
sudo bash install_xray_agent.sh
```

اسکریپت باینری Xray-core را از صفحه release رسمی پروژه `XTLS/Xray-core` دریافت می‌کند و آن را داخل `/opt/rix-storm-agent/xray` قرار می‌دهد؛ باینری سرویسی که از قبل روی VPS اجرا می‌شود را بازنویسی نمی‌کند. این باینری برای فراخوانی API است. اگر با نسخه هسته فعلی سازگار نبود، `XRAY_BIN` را در فایل محیطی به مسیر باینری سازگار خودت تغییر بده. نصب اسکریپت به‌تنهایی به معنی آماده‌شدن نود نیست؛ باید API در Xray فعال باشد و Agent هم تنظیم شود.

### 3. ساخت توکن محرمانه Agent

روی VPS اجرا کن:

```bash
openssl rand -hex 32
```

خروجی را یادداشت کن. سپس فایل `/etc/rix-storm-agent.env` بساز:

```ini
AGENT_TOKEN=اینجا_خروجی_تصادفی_را_قرار_بده
XRAY_API_ADDR=127.0.0.1:10085
XRAY_BIN=/opt/rix-storm-agent/xray
AGENT_STATE_PATH=/opt/rix-storm-agent/inbounds.json
AGENT_PORT_START=20000
AGENT_PORT_END=20100
```

دسترسی فایل را محدود کن:

```bash
sudo chown root:root /etc/rix-storm-agent.env
sudo chmod 600 /etc/rix-storm-agent.env
```

### 4. HTTPS برای Agent

برای Agent یک زیردامنه اختصاص بده؛ مثلاً `agent.example.com` که به VPS اشاره کند. `Caddyfile.example` نمونه reverse proxy است. در آن، نام دامنه را جایگزین کن و Caddy را طوری تنظیم کن که HTTPS معتبر ارائه کند و درخواست‌ها را به `127.0.0.1:9843` بفرستد. Agent را مستقیماً با HTTP عمومی منتشر نکن.

سپس سرویس را فعال کن:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now rix-storm-agent
sudo systemctl status rix-storm-agent --no-pager
```

آدرس `/health` فقط زنده‌بودن Agent را نشان می‌دهد؛ برای ساخت کاربر باید Xray API هم درست کار کند. Agent نسخه پشتیبانی‌شده inboundها را در `/opt/rix-storm-agent/inbounds.json` با دسترسی محدود ذخیره می‌کند و پس از restart هسته برای بازیابی تلاش می‌کند؛ این فایل شامل credentialهای حساس است، پس از آن نسخه پشتیبان عمومی نساز.

### 5. بازکردن محدوده پورت کاربران

در این نمونه محدوده `20000–20100` استفاده شده است. همین محدوده باید در پنل و Agent یکسان باشد. روی فایروال VPS پورت‌ها را برای TCP و UDP باز کن (و در پنل ابری VPS هم Security Group را بررسی کن):

```bash
sudo ufw allow 20000:20100/tcp
sudo ufw allow 20000:20100/udp
```

اگر از UFW استفاده نمی‌کنی، قوانین معادل را در فایروال خودت قرار بده. مطمئن شو این محدوده با برنامه دیگری تداخل ندارد.

## بخش سوم — افزودن سرور داخل پنل

در **سرورها** یک سرور اضافه کن:

- **نام:** اسم دلخواه، مثلاً `DE-01`
- **دامنه یا IP اصلی:** آدرس عمومی VPS که Xray روی آن اجرا می‌شود
- **Proxy IP / دامنه واسط:** اختیاری؛ آدرسی که کلاینت واقعاً باید به آن وصل شود. فقط اگر پراکسی/Port Forwarding برای تمام پورت‌ها درست تنظیم شده است آن را وارد کن.
- **آدرس Agent:** آدرس HTTPS مثل `https://agent.example.com`
- **توکن Agent:** همان `AGENT_TOKEN` موجود در VPS
- **پورت شروع/پایان:** `20000` و `20100`، مطابق تنظیم Agent و فایروال

### تنظیمات TLS و Reality

- **TLS:** در مسیرهای گواهی و کلید، مسیرهای واقعی روی همان VPS را وارد کن و SNI باید با گواهی سازگار باشد.
- **Reality:** کلید عمومی، کلید خصوصی و Short ID باید یک جفت واقعی و متناظر باشند؛ مقدار نمونه نساز. از دستور `xray x25519` نسخه نصب‌شده روی VPS استفاده کن و خروجی را بر اساس قالبی که همان نسخه نشان می‌دهد تنظیم کن. Private Key را محرمانه نگه دار.
- **Proxy IP:** صرفاً یک فیلد نمایش/اتصال نیست؛ اگر آدرس واسط پورت‌های انتخابی را منتقل نکند، کانفیگ اتصال نخواهد داشت.

## بخش چهارم — ساخت کاربر

1. وارد **کاربران و اشتراک‌ها** شو.
2. نام و سرور را انتخاب کن.
3. پروتکل را مشخص کن: VLESS، VMess، Trojan یا Shadowsocks.
4. انتقال و امنیت را انتخاب کن. پنل ترکیب‌های ناسازگار را رد می‌کند؛ Trojan به TLS نیاز دارد و Reality در این نسخه فقط با VLESS فعال است.
5. حجم را به GB و اعتبار را به روز وارد کن. صفر یعنی بدون محدودیت/انقضا در منطق پنل.
6. ساخت کاربر را بزن. پنل ابتدا درخواست inbound را به Agent می‌فرستد و سپس رکورد را ذخیره می‌کند. اگر API در دسترس نباشد، پیام خطا نمایش داده می‌شود.
7. لینک اشتراک را کپی کن یا ساب‌پنل کاربر را باز کن.

## عیب‌یابی سریع

- **اتصال Agent برقرار نمی‌شود:** آدرس باید HTTPS معتبر باشد؛ دامنه، reverse proxy، سرویس `rix-storm-agent` و توکن را بررسی کن.
- **Xray کاربر را نپذیرفت:** `sudo systemctl status xray` و لاگ‌ها را بررسی کن؛ معمولاً API روی `127.0.0.1:10085` یا `HandlerService` درست تنظیم نشده است.
- **کاربر ثبت شد ولی وصل نمی‌شود:** پورت اختصاصی را در فایروال VPS و پنل شبکه باز کن؛ Host/Proxy IP، SNI، TLS certificate و پارامترهای Reality باید واقعاً با سرور هماهنگ باشند.
- **Reality خطا می‌دهد:** public/private key، Short ID و SNI را با مقادیر واقعی یکسان کن.
- **پس از Redeploy اطلاعات ناپدید شده:** Volume باید روی `/data` متصل باشد و `DATA_DIR=/data` تنظیم شده باشد.
- **حجم اشتباه است:** آمار زنده در این نسخه هنوز پیاده نشده؛ مقدار مصرف نمایش‌داده‌شده دستی ثبت می‌شود.

## فایل‌های مهم (همگی در ریشه پروژه)

- `main.py` — پنل وب و عملیات مدیریتی
- `protocols.py` — اعتبارسنجی و تولید inbound/link
- `xray_agent.py` — Agent محافظت‌شده کنار Xray
- `agent_client.py` — اتصال پنل به Agent از طریق HTTPS
- `models.py`, `database.py`, `security.py` — دیتابیس و امنیت
- `Dockerfile`, `requirements.txt`, `start.sh` — استقرار Railway
- `install_xray_agent.sh`, `xray-agent.service.example`, `Caddyfile.example` — راه‌اندازی Agent

برای اجرای تست‌های محلی، پس از نصب وابستگی‌های توسعه:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```
